## 逐卡资源规则

每10秒采样显存、整卡计算利用率及逐进程SM负载。连续3次检查后决定是否增加一个worker；启动后至少等待40秒，测得真实占用再增加。每卡并发安全上限12，实际并发由计算和显存决定，达到约92%整卡负载时不继续堆进程。上限不等于每卡始终开12个进程。

显存至少保留 `max(4GiB, 总显存20%)`；新进程先预算2GiB，随后按实测占用×1.5加256MiB向上调整，尚未进入GPU的启动进程也预留预算。主机内存另保留至少8GiB或15%。这些数值是资源保护参数，不是实验提升门槛。

默认策略不因“卡上已有其他进程”一概禁用。其他进程连续低于20% SM、显存充足且总计算仍有余量时可启动；无法辨认其他进程负载时等待。若其他进程SM超过40%或显存跌破预留值，仅请求**本轮自己的worker**保存检查点后退出，退出码75表示资源让出，之后从同一优化器/RNG状态恢复。v1006002按上方用户覆盖规则允许共享算力。不会终止或修改其他作业。

原模型、损失、数据、训练脚本的70项冻结文件保持字节一致；运营层通过检查点写入钩子释放资源。已验证让出/续训与连续训练权重、指标完全一致。

原环境为PyTorch2.11.0+cu128，其二进制不包含sm70，不能直接放到V100。V100使用同版本PyTorch2.11.0+cu126及相同NumPy1.26.4、Pandas2.1.4、h5py3.15.1。接入前用相同真实输入和固定权重检查预测数值，并验证有限梯度和fused AdamW；GPU检查文件为各服务器的 `operations/GPU_COMPATIBILITY.json`。CUDA构建及实际GPU记录在每个job的runtime.json。

## 跨机器防重与回传

`remote_controller.py`在4090持有中央job锁并写持久化REMOTE_RESERVATION，再向V100发放小批任务。4090调度跳过已远端预留的job；V100只执行仍在其租约清单的任务，清单超过180秒不刷新则停止新启动。中央进程重启后可按预留记录恢复持锁。

只有兼容检查通过的主机才会获得租约；本机已有spec/恢复检查点的任务仍留在本机续训，避免远端重新从头训练或迁移CUDA RNG状态。每台V100至多预留48个未回传任务，每卡并发仍由实时资源决定。
